# Project Manager

## 工作范围

先读已有 AGENTS、README、当前状态和最新讨论，确认项目根目录、已有改动及本次任务。遵从用户最新要求；已有约定不重复询问。结构查找按项目 CodeGraph 规则执行，文档文字用原生搜索。

- **初始化**只建立目录、协作记录、Git 首版和手动清理说明，不自动开始业务开发或生产运行。
- **整理旧项目**沿用有效约定；仅在本次整理范围内迁移，不能为统一名称破坏既有入口。
- **制作或修改本 Skill**不等于初始化当前工作区，也不为其他项目登记删除任务。

## 目录规范

**先按项目类型、实际职责和已有惯例确定目录，再保持稳定。** 类型从项目目标和交付物判断，如资料研究、数据处理、软件开发，不限定分类清单；偶尔使用临时脚本不改变项目类型。无法判断时再询问。

根目录 README 记录类型、实际目录及职责，AGENTS 记录 AI 阅读顺序和协作规则。新项目基础目录为 docs、outputs、skills、reference、data、config；有定期执行的业务任务时，再加入 state、logs。已有项目沿用承担相同职责的有效位置，避免重复建目录；skills 保留。其他目录按项目需要选择，src 等代码目录名称仍只是示例。

| 路径 | 何时需要及职责 |
|---|---|
| `src/` | 业务代码的一种存放方式；有代码时明确存放位置，名称和布局遵从项目或框架约定，不强制使用 src。 |
| `docs/` | 本 Skill 的沟通记录：project-status.md 保存当前结论、证据、阻塞和下一步；discussion-log.md 按时间追加讨论。 |
| `outputs/` | 本 Skill 的任务汇报放 reports/<task-id>.html；有运行结果时才建 runs/<run-id>/。 |
| `reference/` | 基础目录：外部资料及综合研究笔记。 |
| `skills/` | 保留本管理 Skill 和项目专用 Skill，随项目保存。 |
| `data/` | 基础目录：本地输入或正式加工数据；外部已有数据优先引用，试算结果放 outputs。 |
| `config/` | 基础目录：非秘密业务配置；框架要求的根配置保留原位。 |
| `state/` | 定期业务任务加入：增量水位、持久检查点；不是临时垃圾。 |
| `logs/` | 定期业务任务加入：执行日志；普通试算日志仍跟随各次 run。 |

沟通记录、汇报和项目技能都需有明确位置，路径以 README 为准。确定后，后续任务沿用目录约定，不因某轮未使用或暂时为空而增删、改名。只有项目类型或长期职责变化时才调整，更新 README 并记录原因及路径变化；新任务/run 子目录和临时、工具目录按需创建，不算重定项目结构。

Git 不保存空目录，不制造占位文件；克隆后按 README 补齐本项目约定需要的空目录。

docs 保存项目决定，reference 保存外部依据；outputs 保存结果和解释，通过链接关联，不复制正文或数据。项目专用 Skill 保留完整目录并随 Git 保存，以项目副本为该项目的版本依据；AGENTS 链接其入口。全局副本用于技能发现，普通项目维护不自动覆盖全局或复制全部个人技能。

历史使用 Git 提交和标签，不常设平行的 report、result、temp、version、archive 目录。已有项目的这些名称按本次整理范围处理。文件用 UTF-8，目录/代码名简短稳定，内容可用中文；文档用项目相对路径，时间默认 Asia/Shanghai。

### 代码组织的三条规则（有代码时适用）

1. 按职责组织：围绕同一目的、通常一起使用的小步骤合并在一个 `.py`；职责明显不同或确需独立使用、维护时再拆分。
2. **通用步骤**是目的及输入输出约定相同、实际反复使用的处理逻辑。先找已有实现，各流程导入复用；每个步骤只留一份实现，相关步骤可共用文件。
3. 测试和可复用运行工具按项目约定放置，如代码目录下的 `tests/`、`tools/`；工具调用业务实现。框架必需的根入口、依赖和构建文件保留原位置；一次性诊断脚本放临时区。

### 潜在目录

以下职责参考 CTA 截面和期货连续合约项目，供确定类型及目录时选择，不自动创建；后续新增按上面的结构调整规则执行。

| 路径 | 用途与增加条件 |
|---|---|
| `outputs/releases/` | 明确需要独立冻结交付包时，从指定 Git 标签导出。 |
| `.tmp/work/<task-id>/` | 活跃或用途尚未判断的临时内容。 |
| `.tmp/disposable/` | 已完成用途、确定无用，等待用户手动触发清理的内容。 |
| `.codegraph/`、`.venv/`、工具配置目录 | 相应工具需要时建立并保持隐藏。 |

其他类型确有独立职责且现有目录无法容纳时可补充，不预建未来可能用到的架子。

## 初始化流程

1. 确认项目路径、目标、项目类型、是否有定期业务任务及对应目录，再确认**该项目的线上 Git 地址**。先用用户已提供的地址或该项目 origin；缺少时暂停询问 HTTPS/SSH 地址，不借用其他项目地址。
2. 阅读 [Git 与版本保存](references/versioning.md)，检查远端。**本地为空且远端为空**才运行下列脚本；远端已有历史先 clone；本地已有内容则按模板增量补齐，合并 AGENTS/忽略规则并保留已有文件、Skill、改动和历史。

```text
python -X utf8 "<本Skill目录>/scripts/init_project.py" --root "<项目绝对路径>" --remote "<线上Git地址>" --name "<名称>" --purpose "<目标>" --project-type "<项目类型>" [--recurring-tasks] [--folders <其他目录...>]
```

脚本需要 Python 3.10+ 和 Git，默认建立六个基础目录。`--project-type` 填实际类型名称；`--recurring-tasks` 为定期业务任务加上 state/logs，只准备目录，不配置或启动任务；`--folders` 显式补充其他顶层目录，例如 `--folders app`，不替换基础目录。目录名用简短英文，生成后补实职责；若项目采用其他记录/汇报路径，同步调整模板产物及引用。

3. 补实项目类型、目录职责、目标、约束和生成记录，按实际任务填写业务进度。脚本只负责本地结构和 origin，远端检查、提交和推送由执行 AI 接着完成，不能从模板文字推断这些动作已经成功。
4. 按 [维护与清理](references/maintenance.md) 留下手动清理方法；不登记定时清理。更新真实状态和 HTML，检查生成文件及链接后，提交并推送首版。

只有本地结构、项目 Skill、协作记录和首版远程保存都完成，才称“初始化完成”。受阻时交付已完成部分并列明缺项，不伪报成功，也不为补齐而另造系统。

## 每轮讨论与任务收尾

先读当前状态及最新相关讨论，按需读取代码和证据。已采用本规范的项目，每轮实质结论或任务迭代执行：

1. **记录讨论**：使用唯一编号，如 `20261029-1530-layout`；追加时间、用户目标、接受/否决/待定结论及依据、实际改动、验证和下一步。区分用户决定与 AI 建议；结论变化追加取代说明，不覆盖历史。
2. **更新状态**：只保留当前有效结论和证据链接；长任务记清已完成、剩余工作、运行进程及续作方法，接手时避免重复启动。
3. **保存运行与汇报**：有独立结果的运行使用新 run-id，`run.md` 简记命令、参数、输入来源/版本、源码提交或讨论编号、起止及成功/失败，保留必要失败证据。每个完成的任务生成一份 HTML，包括形成正式结论的讨论任务；同任务续作更新其报告，新任务不覆盖旧证据。
4. **整理与保存版本**：必要证据移出临时区，确定无用的内容可归入 disposable 等待手动清理，收尾不默认删除；按 [Git 流程](references/versioning.md) 提交并推送代码、讨论、状态、报告及允许保存的结果，只有文档变化也保存版本。

HTML 用 [模板](assets/report.html.tpl) 或项目已有简明样式：先写结论，再列改动、结果链接、验证和下一步；UTF-8、内联 CSS、离线可读。纯文本做 HTML 转义，链接相对报告位置计算，不指向临时/私密文件；交付前检查内容及链接可读。

寒暄不造版本，工具输出不逐条抄录，普通测试证据可并入本轮记录。单独手动清理按维护规则简报结果，不另造业务版本。最终回复给结论、报告、实际验证、commit 和 push 结果，区分本地成果与线上保存。

## 维护与结束条件

迁移、删除、隐藏属性和手动清理按 [维护规则](references/maintenance.md) 执行；正式冻结、对比和独立交付包按 [版本规则](references/versioning.md) 执行。

优先复用现有结构和脚本。验证应能发现本次具体失败；必要功能和验证完成即交付，不添加无实际用途的哈希、兼容层、重复备份或审查流程。用户和项目明确要求的验证仍执行。
